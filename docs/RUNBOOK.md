## Procedure 1: SSH Brute-Force Attack (Rule 100301)

### Alert Description

Rule 100301 triggers when multiple failed SSH authentication attempts are detected from a single source IP within a short time window (default: >5 failures in 60 seconds). This indicates an active password guessing or credential stuffing attack against an SSH service.

### Severity Rating

| Severity | Level | SLA |
|----------|-------|-----|
| **High** | 12 | Respond within 1 hour |

> Escalates to **Critical (Level 15)** if Rule 100303 (successful login after brute-force) fires from the same source IP.

### Prerequisites

- Access to Wazuh Dashboard (https://localhost:443)
- SSH access to the target host (for forensic investigation)
- Access to firewall/iptables (for IP blocking)
- AbuseIPDB or VirusTotal account (for IP reputation)

### Detailed Steps

#### Step 1: Verify Alert Details

1. Open the alert in Wazuh Dashboard → **Security Events**
2. Confirm the following fields:
   - `data.srcip` — Source IP of the brute-force
   - `agent.name` / `agent.ip` — Target host being attacked
   - `data.dstuser` — User account(s) being targeted
   - `rule.frequency` — Number of failures in the time window
3. Check if multiple user accounts are targeted (credential stuffing vs. targeted attack)

#### Step 2: Check Source IP Reputation

1. Query the source IP against threat intelligence:
   - [AbuseIPDB](https://www.abuseipdb.com/) — Check abuse reports and confidence score
   - [VirusTotal](https://www.virustotal.com/) — Check community votes and associations
   - Wazuh CDB List — Check `config/wazuh/lists/malicious_ips.txt`
2. Record GeoIP location and ISP information
3. Determine if the IP belongs to a known proxy/VPN/Tor exit node

#### Step 3: Look for Successful Login (Rule 100303)

1. Search for Rule 100303 alerts with the same `data.srcip`:
   ```
   rule.id: "100303" AND data.srcip: "<SOURCE_IP>"
   ```
2. If a successful login is found:
   - **Escalate immediately to Critical**
   - Proceed to Step 4 (host isolation)
   - Follow the compromised account investigation workflow
3. If no successful login is found:
   - The attack is ongoing or failed — proceed to Step 5 (block IP)

#### Step 4: If Compromised — Isolate the Host

> ⚠️ **This step is only required if Rule 100303 has fired (successful login detected).**

1. Isolate the host from the network:
   ```bash
   # Add firewall rule to block all outbound traffic except management
   sudo iptables -A OUTPUT -d <MANAGEMENT_SUBNET> -j ACCEPT
   sudo iptables -A OUTPUT -j DROP
   ```
2. **Do NOT power off the host** — preserve volatile memory and active sessions
3. Kill active SSH sessions from the attacker IP:
   ```bash
   # Find and kill attacker sessions
   who | grep <SOURCE_IP>
   sudo pkill -9 -u <COMPROMISED_USER>
   ```
4. Capture forensic state:
   ```bash
   # List running processes
   ps auxf > /tmp/forensic_ps_$(date +%s).txt
   # List network connections
   ss -tunapl > /tmp/forensic_netstat_$(date +%s).txt
   # List recent file modifications
   find / -mmin -60 -type f 2>/dev/null > /tmp/forensic_files_$(date +%s).txt
   ```

#### Step 5: Block Source IP

1. Add the IP to the Wazuh active response blocklist:
   ```bash
   echo "203.0.113.42:" >> config/wazuh/lists/malicious_ips.txt
   ```
2. Block at the firewall level:
   ```bash
   sudo iptables -I INPUT -s <SOURCE_IP> -j DROP
   ```
3. If using Wazuh active response, verify the auto-block triggered:
   ```bash
   cat /var/ossec/logs/active-responses.log | grep <SOURCE_IP>
   ```

#### Step 6: Review Auth Logs for Lateral Movement

1. Search across all hosts for logins from the compromised host IP:
   ```
   data.srcip: "<COMPROMISED_HOST_IP>" AND (rule.id: "5715" OR rule.id: "5716")
   ```
2. Check for SSH sessions initiated from the compromised host:
   ```bash
   grep "ssh" /var/log/auth.log | grep <COMPROMISED_USER>
   ```
3. Review `~/.ssh/known_hosts` on the compromised host for previously connected systems

#### Step 7: Reset Affected Credentials

1. Lock the compromised user account:
   ```bash
   sudo usermod -L <COMPROMISED_USER>
   ```
2. Force password reset:
   ```bash
   sudo passwd -e <COMPROMISED_USER>
   ```
3. Rotate any SSH keys associated with the account
4. If `/etc/shadow` was accessed, reset all passwords on the host

#### Step 8: Document and Escalate

1. Create an incident report using the [Incident Report Template](INCIDENT_REPORT_TEMPLATE.md)
2. Escalate to the IR team if:
   - The attacker achieved successful login (Rule 100303)
   - Lateral movement was detected
   - Persistence mechanisms were installed
   - Data exfiltration is suspected

### Escalation Criteria

| Condition | Escalation Level |
|-----------|-----------------|
| Brute-force only (no success) | Standard — block IP and monitor |
| Successful login detected (100303) | **Immediate — IR team notification** |
| Lateral movement detected | **Immediate — IR team + management** |
| Data exfiltration suspected | **Immediate — IR team + legal/compliance** |

### Resolution Checklist

- [ ] Source IP blocked (firewall + CDB list)
- [ ] No successful logins from attacker IP
- [ ] Compromised accounts locked and credentials reset
- [ ] No lateral movement detected
- [ ] No persistence mechanisms found
- [ ] Auth logs reviewed across all connected hosts
- [ ] Incident report completed
- [ ] Detection rule tuning reviewed (threshold adjustments)

### Related Rules

| Rule ID | Relationship |
|---------|-------------|
| 100302 | RDP Brute-Force — parallel detection for Windows |
| 100303 | Successful Login After Brute-Force — critical escalation trigger |
| 100101 | Crontab Modification — post-compromise persistence indicator |
| 100102 | SSH Authorized Keys Modified — post-compromise persistence indicator |

## Procedure 2: Credential Dumping — Mimikatz (Rule 100001)

### Alert Description

Rule 100001 triggers when Mimikatz execution is detected on a Windows endpoint. Detection is based on process creation events (Sysmon EID 1) matching known Mimikatz command-line patterns (`sekurlsa::logonpasswords`, `kerberos::list`, `lsadump::sam`), process names, or binary hashes. This is a critical indicator of active credential theft.

### Severity Rating

| Severity | Level | SLA |
|----------|-------|-----|
| **Critical** | 15 | Respond within 15 minutes |

> This is always a **Critical** alert. Mimikatz detection in a production environment indicates an active adversary with elevated privileges.

### Prerequisites

- Access to Wazuh Dashboard
- Remote access to the affected Windows host (RDP, WinRM, or EDR console)
- Ability to force password resets (Active Directory admin or equivalent)
- Memory capture tool (e.g., WinPmem, Belkasoft RAM Capturer)

### Detailed Steps

#### Step 1: Isolate the Affected Host Immediately

> ⚠️ **Time-critical.** Mimikatz extracts credentials from memory in seconds. Immediate isolation prevents lateral movement with stolen credentials.

1. **Network isolation** — Disconnect the host from the network:
   - Via EDR: Initiate network containment
   - Via switch: Disable the port
   - Via host: `netsh interface set interface "Ethernet" admin=disable`
2. **Do NOT reboot** — Preserve memory for forensic analysis
3. Notify the IR team immediately

#### Step 2: Capture Memory Dump

1. Deploy a memory capture tool to the isolated host:
   ```powershell
   # Using WinPmem (example)
   .\winpmem_mini.exe memdump_$(hostname)_$(Get-Date -Format yyyyMMdd_HHmmss).raw
   ```
2. Capture the Mimikatz process:
   ```powershell
   # Find the Mimikatz process (may be renamed)
   Get-Process | Where-Object { $_.Path -like "*mimikatz*" -or $_.CommandLine -like "*sekurlsa*" }
   # Create process dump
   procdump.exe -ma <PID> mimikatz_dump.dmp
   ```
3. Preserve the memory dump in a forensic evidence share

#### Step 3: Identify Compromised Credentials

1. Determine which credentials were in memory at the time of the dump:
   - All users logged in interactively (current and recent sessions)
   - Service accounts running on the host
   - Cached domain credentials
2. List affected accounts:
   ```powershell
   # Recently logged-in users
   Get-WmiObject -Class Win32_UserProfile | Select-Object LocalPath, LastUseTime
   # Active sessions
   query user
   ```
3. Create a comprehensive list of all potentially compromised accounts

#### Step 4: Check for Lateral Movement

1. Search for Event ID 4624 (Logon) Type 3 (Network) events from the compromised host:
   ```
   event.code: "4624" AND winlog.event_data.LogonType: "3" AND source.ip: "<COMPROMISED_HOST_IP>"
   ```
2. Search for remote service creation (Event ID 7045) on other hosts:
   ```
   event.code: "7045" AND winlog.event_data.AccountName: "<COMPROMISED_ACCOUNTS>"
   ```
3. Check for PsExec, WMI, or PowerShell remoting from the compromised host
4. Review SMB connection logs for file share access

#### Step 5: Force Password Reset for All Affected Accounts

1. **Immediately reset** passwords for all accounts identified in Step 3:
   ```powershell
   # Reset AD user password
   Set-ADAccountPassword -Identity <username> -Reset -NewPassword (ConvertTo-SecureString "TempP@ss!" -AsPlainText -Force)
   Set-ADUser -Identity <username> -ChangePasswordAtLogon $true
   ```
2. **Revoke all active Kerberos tickets** (the attacker may have Golden/Silver tickets):
   ```powershell
   # Reset the krbtgt account password (TWICE, 12 hours apart)
   # WARNING: This will invalidate ALL existing Kerberos tickets domain-wide
   Reset-KrbtgtAccountPassword  # Only if Golden Ticket is suspected
   ```
3. Reset service account passwords and update dependent services

#### Step 6: Review for Persistence Mechanisms

1. Check for new scheduled tasks:
   ```powershell
   Get-ScheduledTask | Where-Object { $_.Date -gt (Get-Date).AddDays(-1) }
   ```
2. Check for new services:
   ```powershell
   Get-Service | Where-Object { $_.Status -eq 'Running' } | Sort-Object -Property DisplayName
   ```
3. Check for WMI event subscriptions:
   ```powershell
   Get-WmiObject -Namespace root\subscription -Class __EventFilter
   Get-WmiObject -Namespace root\subscription -Class CommandLineEventConsumer
   ```
4. Check for registry run keys:
   ```powershell
   Get-ItemProperty "HKLM:\Software\Microsoft\Windows\CurrentVersion\Run"
   Get-ItemProperty "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run"
   ```

#### Step 7: Rebuild If Necessary

1. If persistence is confirmed or the full scope of compromise is unclear:
   - **Rebuild the host from a known-good image**
   - Do NOT attempt to "clean" a compromised host in production
2. Restore from backup only if the backup predates the initial compromise
3. Re-deploy the Wazuh agent and validate Sysmon configuration

#### Step 8: Escalate to IR Team

1. Provide the IR team with:
   - Memory dumps
   - Timeline of events
   - List of compromised accounts
   - Evidence of lateral movement
   - Persistence mechanisms found
2. The IR team will determine if a full incident investigation is warranted

### Escalation Criteria

| Condition | Escalation Level |
|-----------|-----------------|
| Mimikatz detected (any) | **Immediate — IR team notification** |
| Domain admin credentials compromised | **Critical — IR team + domain admin team** |
| Lateral movement confirmed | **Critical — IR team + management** |
| Golden/Silver Ticket suspected | **Critical — IR team + domain admin + CISO** |

### Resolution Checklist

- [ ] Affected host isolated from network
- [ ] Memory dump captured and preserved
- [ ] All compromised accounts identified
- [ ] Passwords reset for all affected accounts
- [ ] Kerberos tickets invalidated (if domain compromise suspected)
- [ ] No lateral movement confirmed (or fully scoped)
- [ ] Persistence mechanisms removed or host rebuilt
- [ ] Wazuh agent redeployed and Sysmon validated
- [ ] Incident report completed
- [ ] Post-incident review scheduled

### Related Rules

| Rule ID | Relationship |
|---------|-------------|
| 100004 | LSASS Memory Access — precursor to credential dumping |
| 100005 | Suspicious Parent-Child Process — may detect the initial execution vector |
| 100002 | Encoded PowerShell — may detect Mimikatz delivery via PowerShell |
| 100003 | New Service Created — post-compromise persistence |

## Procedure 3: AWS Console Login Without MFA (Rule 100201)

### Alert Description

Rule 100201 triggers when an IAM user logs into the AWS Management Console without Multi-Factor Authentication. This is detected via CloudTrail `ConsoleLogin` events where `additionalEventData.MFAUsed` is `No`. Non-MFA logins significantly increase the risk of account takeover from compromised or leaked credentials.

### Severity Rating

| Severity | Level | SLA |
|----------|-------|-----|
| **High** | 12 | Respond within 1 hour |

> Escalates to **Critical** if the login is from an unexpected location, the IAM user has admin privileges, or suspicious API calls follow the login.

### Prerequisites

- Access to Wazuh Dashboard
- AWS Console access with IAM read permissions
- Access to CloudTrail event history
- Knowledge of organizational MFA policy

### Detailed Steps

#### Step 1: Identify the IAM User

1. Extract the IAM user from the alert:
   - `data.aws.userIdentity.userName` — The IAM user who logged in
   - `data.aws.userIdentity.arn` — Full ARN of the identity
   - `data.aws.sourceIPAddress` — Source IP of the login
   - `data.aws.userIdentity.accountId` — AWS account ID
2. Check GeoIP of the source IP — does it match the user's expected location?
3. Check the user-agent string for the browser/OS used

#### Step 2: Verify If the Login Is Authorized

1. **Contact the IAM user** (if identifiable) to confirm the login:
   - Did they log in at this time?
   - Why wasn't MFA used? (hardware token failure, new device, etc.)
   - Were they aware of the MFA requirement?
2. **Check the IAM user's MFA status**:
   ```bash
   aws iam list-mfa-devices --user-name <USERNAME>
   ```
   - If no MFA device is registered → policy violation, enforce MFA
   - If MFA device exists but wasn't used → potential credential compromise

#### Step 3: Check CloudTrail for Subsequent Actions

1. Query CloudTrail for all API calls by this user in the hours following the login:
   ```bash
   aws cloudtrail lookup-events \
     --lookup-attributes AttributeKey=Username,AttributeValue=<USERNAME> \
     --start-time <LOGIN_TIME> \
     --end-time <LOGIN_TIME + 4 hours>
   ```
2. Look for high-risk actions:
   - IAM changes (CreateUser, AttachPolicy, CreateAccessKey)
   - S3 changes (PutBucketPolicy, PutBucketAcl)
   - EC2 launches (RunInstances) — especially large instances
   - CloudTrail changes (StopLogging, DeleteTrail)
   - Security group modifications
3. Flag any action that deviates from the user's normal activity pattern

#### Step 4: If Unauthorized — Immediate Containment

1. **Disable the IAM user's access keys**:
   ```bash
   aws iam update-access-key --user-name <USERNAME> --access-key-id <KEY_ID> --status Inactive
   ```
2. **Disable the console password**:
   ```bash
   aws iam delete-login-profile --user-name <USERNAME>
   ```
3. **Revoke all active sessions**:
   - Attach an inline deny-all policy with a condition on `aws:TokenIssueTime` before the current time
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Effect": "Deny",
       "Action": "*",
       "Resource": "*",
       "Condition": {
         "DateLessThan": {"aws:TokenIssueTime": "<CURRENT_TIMESTAMP>"}
       }
     }]
   }
   ```

#### Step 5: Enforce MFA on the Account

1. If the user doesn't have MFA registered:
   ```bash
   # Attach MFA enforcement policy
   aws iam attach-user-policy --user-name <USERNAME> \
     --policy-arn arn:aws:iam::aws:policy/IAMUserChangePassword
   ```
2. Send the user instructions for registering a virtual MFA device
3. Verify MFA is enforced before re-enabling console access

#### Step 6: Review IAM Policies

1. List the user's attached policies:
   ```bash
   aws iam list-attached-user-policies --user-name <USERNAME>
   aws iam list-user-policies --user-name <USERNAME>
   aws iam list-groups-for-user --user-name <USERNAME>
   ```
2. Apply principle of least privilege — remove any excessive permissions
3. Consider implementing an SCP that denies console access without MFA

#### Step 7: Check for Resource Creation/Modification

1. Audit any resources created or modified during the unauthorized session:
   - New EC2 instances (check for crypto miners)
   - New IAM users or roles (persistence)
   - S3 bucket policy changes (data exposure)
   - Lambda functions (backdoors)
2. Revert any unauthorized changes
3. Terminate any unauthorized resources

### Escalation Criteria

| Condition | Escalation Level |
|-----------|-----------------|
| No-MFA login, user confirms it was them | Standard — enforce MFA, document |
| No-MFA login from unexpected location | **High — investigate as potential compromise** |
| Unauthorized API calls after login | **Critical — IR team notification** |
| Admin-level IAM user compromised | **Critical — IR team + cloud security team** |

### Resolution Checklist

- [ ] IAM user identified and contacted
- [ ] Login authorization confirmed or denied
- [ ] CloudTrail activity reviewed for post-login actions
- [ ] Access keys disabled (if unauthorized)
- [ ] Active sessions revoked (if unauthorized)
- [ ] MFA enforced on the account
- [ ] IAM policies reviewed and tightened
- [ ] No unauthorized resources created
- [ ] Incident report completed

### Related Rules

| Rule ID | Relationship |
|---------|-------------|
| 100203 | New IAM User Created — may follow unauthorized login |
| 100204 | Root Account Usage — parallel detection for root identity |
| 100207 | CloudTrail Logging Disabled — attacker may try to cover tracks |
| 100208 | Excessive AccessDenied — reconnaissance after login |

## Procedure 4: S3 Bucket Made Public (Rule 100202)

### Alert Description

Rule 100202 triggers when an S3 bucket's ACL or policy is modified to allow public access. This is detected via CloudTrail events for `PutBucketPolicy`, `PutBucketAcl`, `PutObjectAcl`, or `DeletePublicAccessBlock` that result in public-readable or public-writable configurations. Public S3 buckets are one of the most common causes of cloud data breaches.

### Severity Rating

| Severity | Level | SLA |
|----------|-------|-----|
| **Critical** | 15 | Respond within 15 minutes |

> This is always a **Critical** alert. Data exposure can result in regulatory violations, reputational damage, and legal liability.

### Prerequisites

- Access to Wazuh Dashboard
- AWS Console access with S3 and CloudTrail read permissions
- Knowledge of the organization's S3 public access policy
- S3 access logs enabled (for exposure assessment)

### Detailed Steps

#### Step 1: Immediately Revert Bucket ACL/Policy

> ⚠️ **Time-critical.** Every minute the bucket is public, data may be accessed by unauthorized parties.

1. **Revert the bucket policy**:
   ```bash
   # Remove the public policy
   aws s3api delete-bucket-policy --bucket <BUCKET_NAME>
   # Or replace with the previous known-good policy
   aws s3api put-bucket-policy --bucket <BUCKET_NAME> --policy file://previous_policy.json
   ```
2. **Reset the bucket ACL to private**:
   ```bash
   aws s3api put-bucket-acl --bucket <BUCKET_NAME> --acl private
   ```
3. **Verify public access is blocked**:
   ```bash
   aws s3api get-bucket-policy-status --bucket <BUCKET_NAME>
   aws s3api get-public-access-block --bucket <BUCKET_NAME>
   ```

#### Step 2: Identify Who Made the Change

1. Query CloudTrail for the change event:
   ```bash
   aws cloudtrail lookup-events \
     --lookup-attributes AttributeKey=ResourceName,AttributeValue=<BUCKET_NAME> \
     --start-time <ALERT_TIME - 1 hour>
   ```
2. Extract:
   - `userIdentity` — Who made the change (IAM user, role, or service)
   - `sourceIPAddress` — Where the change came from
   - `userAgent` — How the change was made (Console, CLI, SDK, Terraform)
3. Determine if the change was intentional or unauthorized

#### Step 3: Audit Bucket Contents for Sensitive Data

1. List the bucket contents:
   ```bash
   aws s3 ls s3://<BUCKET_NAME> --recursive --summarize
   ```
2. Check for sensitive data categories:
   - PII (names, emails, SSNs, phone numbers)
   - Financial records (credit cards, bank accounts)
   - Credentials (API keys, passwords, certificates)
   - Healthcare data (PHI, medical records)
   - Proprietary/confidential business data
3. If sensitive data is found, classify the data exposure severity

#### Step 4: Check Access Logs for Unauthorized Downloads

1. If S3 server access logging is enabled, review logs for access during the public window:
   ```bash
   aws s3 cp s3://<LOG_BUCKET>/s3-access-logs/ ./access-logs/ --recursive
   grep "GET" ./access-logs/* | grep -v "<KNOWN_INTERNAL_IPS>"
   ```
2. Check for:
   - External IP addresses accessing objects
   - Bulk download patterns (many sequential GET requests)
   - Access to sensitive files identified in Step 3
3. If CloudFront was in front of the bucket, review CloudFront access logs as well

#### Step 5: Enable S3 Block Public Access

1. Enable account-level public access block:
   ```bash
   aws s3control put-public-access-block \
     --account-id <ACCOUNT_ID> \
     --public-access-block-configuration \
       BlockPublicAcls=true,\
       IgnorePublicAcls=true,\
       BlockPublicPolicy=true,\
       RestrictPublicBuckets=true
   ```
2. Enable bucket-level public access block:
   ```bash
   aws s3api put-public-access-block \
     --bucket <BUCKET_NAME> \
     --public-access-block-configuration \
       BlockPublicAcls=true,\
       IgnorePublicAcls=true,\
       BlockPublicPolicy=true,\
       RestrictPublicBuckets=true
   ```

#### Step 6: Review Service Control Policies (SCPs)

1. Check if SCPs exist to prevent public S3 access:
   ```bash
   aws organizations list-policies --filter SERVICE_CONTROL_POLICY
   ```
2. If no SCP exists, create one to deny public S3 actions:
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Sid": "DenyS3PublicAccess",
       "Effect": "Deny",
       "Action": [
         "s3:PutBucketPolicy",
         "s3:PutBucketAcl",
         "s3:PutObjectAcl",
         "s3:DeletePublicAccessBlock"
       ],
       "Resource": "*",
       "Condition": {
         "StringNotEquals": {
           "aws:PrincipalArn": "arn:aws:iam::*:role/SecurityAdmin"
         }
       }
     }]
   }
   ```

#### Step 7: Notify Data Owner

1. Identify the bucket owner from tags or the IAM principal that created it
2. Notify the data owner of the exposure window:
   - When the bucket was made public
   - When it was reverted to private
   - What data was potentially exposed
   - Whether unauthorized access was detected
3. If sensitive data was exposed, initiate the data breach notification process per organizational policy

### Escalation Criteria

| Condition | Escalation Level |
|-----------|-----------------|
| Public bucket with no sensitive data | High — revert and document |
| Public bucket with sensitive data, no unauthorized access | **Critical — IR team + data owner + legal** |
| Public bucket with confirmed unauthorized downloads | **Critical — IR team + legal + compliance + CISO** |
| PII/PHI/PCI data exposed | **Critical — regulatory breach notification may be required** |

### Resolution Checklist

- [ ] Bucket ACL/policy reverted to private
- [ ] S3 Block Public Access enabled (bucket + account level)
- [ ] Change attribution identified via CloudTrail
- [ ] Bucket contents audited for sensitive data
- [ ] Access logs reviewed for unauthorized downloads
- [ ] SCP implemented to prevent future public access
- [ ] Data owner notified
- [ ] Breach notification initiated (if required)
- [ ] Incident report completed

### Related Rules

| Rule ID | Relationship |
|---------|-------------|
| 100201 | AWS Console Login Without MFA — may precede unauthorized S3 changes |
| 100207 | CloudTrail Logging Disabled — attacker may try to hide the trail |
| 100203 | New IAM User Created — may be used to re-access the bucket |
| 100208 | Excessive AccessDenied — reconnaissance before finding the right bucket |

## Procedure 5: GuardDuty Crypto Mining Detection (Rule 100205)

### Alert Description

Rule 100205 triggers when AWS GuardDuty detects an EC2 instance communicating with known cryptocurrency mining pools. The GuardDuty finding type is `CryptoCurrency:EC2/BitcoinTool.B!DNS` or similar variants. This is a strong indicator that the instance has been compromised and is being used for unauthorized resource hijacking.

### Severity Rating

| Severity | Level | SLA |
|----------|-------|-----|
| **Critical** | 15 | Respond within 15 minutes |

> This is always a **Critical** alert. Crypto mining on compromised instances indicates active exploitation with potential for significant financial impact (inflated compute costs) and credential theft.

### Prerequisites

- Access to Wazuh Dashboard
- AWS Console access with EC2, IAM, and VPC read permissions
- Ability to modify security groups and terminate instances
- Access to AWS billing dashboard

### Detailed Steps

#### Step 1: Identify the Affected Instance

1. Extract instance details from the alert:
   - `data.aws.resource.instanceDetails.instanceId` — EC2 Instance ID
   - `data.aws.resource.instanceDetails.imageId` — AMI used
   - `data.aws.resource.instanceDetails.instanceType` — Instance size (crypto miners often use GPU instances)
   - `data.aws.resource.instanceDetails.launchTime` — When the instance was launched
   - `data.aws.service.action.networkConnectionAction.remoteIpDetails` — Mining pool IP
2. Identify the instance owner from tags (Name, Owner, Environment)
3. Determine if this is a known/authorized instance

#### Step 2: Isolate the Instance from the Network

> ⚠️ **Time-critical.** The mining process is actively consuming compute resources and may be exfiltrating credentials.

1. **Replace the security group** with an isolation group that allows no inbound/outbound traffic:
   ```bash
   # Create isolation security group (if not already created)
   aws ec2 create-security-group \
     --group-name "forensic-isolation" \
     --description "No inbound or outbound traffic" \
     --vpc-id <VPC_ID>

   # Apply isolation security group (replaces all existing SGs)
   aws ec2 modify-instance-attribute \
     --instance-id <INSTANCE_ID> \
     --groups <ISOLATION_SG_ID>
   ```
2. **Do NOT terminate the instance yet** — preserve it for forensic analysis
3. Note the original security groups for documentation

#### Step 3: Check for Unauthorized Processes

1. If SSM Agent is available, connect to the instance:
   ```bash
   aws ssm start-session --target <INSTANCE_ID>
   ```
2. Look for mining processes:
   ```bash
   # High CPU processes
   top -b -n 1 | head -20
   # Known mining process names
   ps aux | grep -iE 'xmrig|minerd|cpuminer|cgminer|bfgminer|stratum'
   # Suspicious network connections to mining pools
   ss -tunapl | grep -E ':(3333|4444|5555|8333|9999)'
   ```
3. Capture process details and network connections for evidence

#### Step 4: Review Security Groups for Open Ports

1. List the instance's original security groups:
   ```bash
   aws ec2 describe-security-groups --group-ids <ORIGINAL_SG_IDS>
   ```
2. Check for overly permissive rules:
   - SSH (22) open to 0.0.0.0/0
   - RDP (3389) open to 0.0.0.0/0
   - All traffic (0-65535) open to any source
3. Identify the likely initial access vector based on open ports

#### Step 5: Check for IAM Credential Abuse

1. Identify the instance's IAM role:
   ```bash
   aws ec2 describe-instances --instance-ids <INSTANCE_ID> \
     --query 'Reservations[0].Instances[0].IamInstanceProfile.Arn'
   ```
2. Check if the instance role credentials were used for suspicious API calls:
   ```bash
   aws cloudtrail lookup-events \
     --lookup-attributes AttributeKey=ResourceName,AttributeValue=<ROLE_ARN> \
     --start-time <INSTANCE_COMPROMISE_TIME>
   ```
3. Look for:
   - IAM changes (escalation attempts)
   - S3 access (data exfiltration)
   - EC2 launches (spreading to new instances)
   - Lambda creation (persistence)

#### Step 6: Terminate the Instance (If Compromised)

1. After forensic evidence is captured:
   ```bash
   # Create a snapshot for forensic preservation
   aws ec2 create-snapshot \
     --volume-id <VOLUME_ID> \
     --description "Forensic snapshot - INC-YYYY-NNNN - crypto mining compromise"

   # Terminate the compromised instance
   aws ec2 terminate-instances --instance-ids <INSTANCE_ID>
   ```
2. **Do NOT reuse the AMI** that was used to launch the compromised instance without investigation

#### Step 7: Launch Clean Replacement

1. Launch a replacement instance from a known-good, patched AMI
2. Apply hardened security groups:
   - Restrict SSH to bastion/VPN IP ranges only
   - Apply principle of least privilege for outbound rules
3. Ensure the Wazuh agent is installed and reporting
4. Verify the instance role has minimal required permissions

#### Step 8: Review Billing for Anomalies

1. Check AWS Cost Explorer for unusual compute charges:
   ```bash
   aws ce get-cost-and-usage \
     --time-period Start=<30_DAYS_AGO>,End=<TODAY> \
     --granularity DAILY \
     --metrics BlendedCost \
     --filter '{"Dimensions":{"Key":"SERVICE","Values":["Amazon Elastic Compute Cloud - Compute"]}}'
   ```
2. Look for:
   - Sudden spikes in EC2 costs
   - GPU instance usage (p3, p4, g4, g5 families)
   - Charges from unexpected regions
3. Set up billing alerts if not already configured

### Escalation Criteria

| Condition | Escalation Level |
|-----------|-----------------|
| Single instance compromised, no credential abuse | High — contain and replace |
| IAM credentials from instance used for further access | **Critical — IR team + cloud security** |
| Multiple instances compromised (spreading) | **Critical — IR team + cloud security + management** |
| Significant billing impact (>$1000) | **Critical — IR team + finance + management** |

### Resolution Checklist

- [ ] Affected instance identified and isolated
- [ ] Forensic snapshot captured
- [ ] Mining processes identified and documented
- [ ] Security groups reviewed and attack vector identified
- [ ] IAM role credentials checked for abuse
- [ ] Compromised instance terminated
- [ ] Clean replacement launched with hardened configuration
- [ ] Billing reviewed for anomalies
- [ ] Billing alerts configured
- [ ] Security group rules tightened across the VPC
- [ ] Incident report completed
